# سند طراحی آیرون‌پین

این سند طراحی کامل اپ است: چه چیزی ساخته شده، چرا این‌طور ساخته شده، و کدام
تصمیم‌ها عمداً گرفته نشده‌اند. هدف این است که هر تغییر بعدی از روی همین سند قابل
داوری باشد، نه از روی حدس.

آخرین به‌روزرسانی: نسخهٔ ۰.۹.۰ — 2026-11-10

وضعیت آزمون: `flutter analyze` پاک و ۳۶۸ آزمون موفق‌اند؛ APK آزمایشی
`armeabi-v7a` ساخته و به‌صورت ایستا بررسی شد. نصب/اجرای دستگاهی انجام نشده است.
جزئیات و SHA-256 در [گزارش آزمون ۰.۹.۰](TEST_REPORT.v0.9.0.fa.md) آمده‌اند.

## ۱) مسئله و دامنه

آیرون‌پین قیمت فولاد را از منابع عمومی ایرانی می‌خواند و سه کار با آن می‌کند:

1. **قیمت‌ها** — فهرست اعلام‌های قیمت، با فیلتر بر اساس محصول، شهر، سایز و بازهٔ زمانی.
2. **رنج‌گیری** — از یک محصول مشخص (مثلاً «تیرآهن ۱۴ ذوب آهن اصفهان») یک بازهٔ
   قیمتی می‌سازد: حداقل، حداکثر، میانگین، تعداد فروشنده.
3. **محاسبات** — وزن و قیمت یک قطعه از روی ابعاد.

اپ **آفلاین-اول** است: هر چه خوانده می‌شود در SQLite محلی می‌ماند و پاسخ‌ها از
همان آرشیو مشتق می‌شوند. هیچ سروری در کار نیست.

### آنچه در دامنه نیست

- هیچ ورود به حساب کاربری، دور زدن CAPTCHA یا استفاده از API خصوصی.
- هیچ حدس زدن دادهٔ اعلام‌نشده (بند ۲).
- هیچ نمایش قیمت به عنوان «نظر اپ». هر عدد یا از منبع آمده یا نیست.

## ۲) اصول طراحی

این اصول بر هر تصمیم فنی مقدم‌اند. هر تغییر باید با آن‌ها سازگار باشد.

### ۲.۱ حدس ممنوع

- **واحد پول از بزرگی عدد استنتاج نمی‌شود.** اگر منبع «تومان» یا «ریال» ننوشته،
  `currency` همان `نامشخص` می‌ماند. استنتاج تومان ریسک خطای ۱۰ برابری دارد و یک
  خطای ۱۰ برابری در قیمت فولاد بدتر از یک خانهٔ خالی است.
- **طول پیش‌فرض وجود ندارد.** اگر منبع وزن هر شاخه را نگفته، تبدیل «شاخه به
  کیلوگرم» انجام نمی‌شود؛ ردیف با واحد خودش می‌ماند و وارد مقایسهٔ کیلویی نمی‌شود.
- **سایز جعلی ساخته نمی‌شود.** در ردیف‌های فهرستی، عدد ابتدایی برای «ورق» ضخامت
  است و برای «نبشی» بُعد دو بال. ساختن یک `sizeLabel` کلی، این دو را جابه‌جا
  می‌کند. قالب غالب واقعی (`تیرآهن ۱۴ ذوب آهن اصفهان ⬅ …`) سایزش را می‌خواند.
- **مقدار نامعلوم، نامعلوم می‌ماند.** `amount == null` یک وضعیت معتبر است، نه یک
  خطا. شمارش‌ها آن را جدا گزارش می‌کنند (`undated`، `unpriced`).

### ۲.۲ منبع تنها حقیقت پول است

جدول‌های `latest` و `history` تنها مرجع پول هستند. هر چیز دیگری — ایندکس،
پاسخ‌های کش‌شده، تصویر رنج — **مشتق** است و هر لحظه قابل دور ریختن و ساختن
دوباره از payloadها.

نتیجهٔ عملی: ایندکس در بکاپ نمی‌آید. بازگردانی یک بکاپ، ایندکس را در اولین
خواندن از نو می‌سازد.

### ۲.۳ اشتقاق یک‌بار، در لحظهٔ نوشتن

هر ردیف در `saveSnapshot` یک‌بار اشتقاق و در `range_index` ذخیره می‌شود. خواندن
آرشیو برای رنج‌گیری دیگر payload را parse نمی‌کند.

### ۲.۴ مسیر سریع باید همان پاسخ مسیر کند باشد

تب قیمت دو مسیر دارد: کلاسیک (فیلتر روی `Quote`) و ایندکسی (روی ستون‌های
مشتق). مسیر ایندکسی یک **بهینه‌سازی** است، نه یک قاعدهٔ دیگر. اگر نتواند دقیقاً
همان فهرست را بدهد، باید کنار برود — و این تساوی تست شده است
(`test/range_all_candidates_test.dart`).

### ۲.۵ ناشناخته‌ها صریح گفته می‌شوند

هر شمارش «چند ردیف رد شد و چرا» را نگه می‌دارد. هیچ‌جا یک ردیف بی‌صدا حذف
نمی‌شود.

## ۳) معماری

سه لایه، با وابستگی یک‌طرفه:

```
lib/ui/     ──►  lib/data/     ──►  lib/domain/
(Flutter)        (SQLite، شبکه)     (Dart خالص، بدون Flutter)
```

`lib/domain/` هیچ import از Flutter ندارد. این یعنی همهٔ قواعد پول، محصول و
آمار در تست‌های بدون ویجت قابل اجرا هستند و روی ایزولیت پس‌زمینه هم کار می‌کنند.

| لایه | فایل‌ها | مسئولیت |
| --- | --- | --- |
| `domain` | ۱۲ فایل | `Quote`، `MarketFilter`، `ProductFacts`، `RowFacts`، تصویر رنج، موتور متن، ماشین‌حساب |
| `data` | ۸ فایل | `MarketStore` (SQLite)، `SourceClient` (شبکه)، `MarketController`، `RangeSession`، بکاپ، لاگر |
| `ui` | ۷ فایل | پنج تب، ویجت‌های مشترک، پنل بکاپ |

### تب‌ها

پنج تب در `NavigationBar`: **قیمت‌ها**، **نمودار**، **رنج‌گیری**، **محاسبات**،
**اطلاعات**.

## ۴) مدل داده

### ۴.۱ جدول‌ها (schema نسخهٔ ۷)

**`latest`** — ردیف فعلی هر اعلام.

```sql
CREATE TABLE latest (
  id TEXT PRIMARY KEY, endpoint TEXT NOT NULL,
  payload TEXT NOT NULL, active INTEGER NOT NULL DEFAULT 1
)
```

`payload` همان JSON کامل `Quote` است. `active=0` یعنی اعلام از فهرست فعلی کنار
رفته ولی **تاریخچه‌اش پاک نشده**.

**`history`** — یک ردیف به‌ازای هر تغییر واقعی قیمت.

```sql
CREATE TABLE history (
  seq INTEGER PRIMARY KEY AUTOINCREMENT, id TEXT NOT NULL,
  captured_at TEXT NOT NULL, signature TEXT NOT NULL,
  payload TEXT NOT NULL, market_at TEXT
)
```

`signature` اثر انگشت محتوای قیمت‌دار است؛ اگر تغییر نکند، ردیف تاریخچهٔ تازه
ساخته نمی‌شود. این یعنی نوسازیِ بدون تغییر، تاریخچه تولید نمی‌کند.

**`settings`** — کلید/مقدار: شهر انتخابی، پنجرهٔ زمانی، فهرست منابع فعال،
نسخهٔ مهاجرت‌ها، زمان آخرین نوسازی.

**`sync`** — وضعیت هر منبع: `attempted_at`، `success_at`، `message`. یک منبع
ناموفق همین‌جا گزارش می‌شود؛ دادهٔ قبلی‌اش دست‌نخورده می‌ماند.

**`range_index`** — ایندکس مشتق (بند ۶).

### ۴.۲ ایندکس‌ها

```sql
range_index_family   ON range_index(family, market_at)
range_index_category ON range_index(category, market_at)
history_market_time  ON history(market_at)
history_id_time      ON history(id, captured_at)
history_id_seq       ON history(id, seq)
latest_endpoint_active ON latest(endpoint, active)
```

در ایندکس‌های رنج، ستون فیلتر اول است و `market_at` آخر، چون پنجرهٔ زمانی
یک **بازه** روی آن است. schema 7 ایندکس endpoint/active را اضافه کرد و schema 8
جدول lease هم‌زمانی `refresh_lock` را برای نوسازی دستی/پس‌زمینه افزود؛ payload،
تاریخچه و قرارداد بکاپ تغییر نمی‌کنند.

### ۴.۳ سیاست مهاجرت

- مهاجرت‌ها **افزودنی** هستند؛ هیچ payload بازنویسی نمی‌شود.
- وضعیت مشتق با یک نسخهٔ اشتقاق (`RowFacts.derive`) نشانه‌گذاری می‌شود. ردیفی که
  با اشتقاق قدیمی‌تر نوشته شده، در اولین خواندن یک‌بار بازسازی می‌شود — نه در
  مهاجرت.
- **ترتیب بلوک‌های `onUpgrade` بر اساس وابستگی جدول است، نه شمارهٔ نسخه.** بلوکی
  که `ALTER TABLE range_index` می‌زند باید بعد از بلوکی بیاید که جدول را می‌سازد؛
  وگرنه آرشیو قدیمی‌تر از نسخهٔ ۴ با `no such table: range_index` می‌شکند. این
  اشتباه یک‌بار رخ داده و با تست پوشش داده شده.

## ۵) موتور متن

`lib/domain/text_engine.dart` متنی را که یک کانال منتشر کرده به ردیف‌های قیمت
تبدیل می‌کند. سند تفصیلی‌اش `docs/TEXT_ENGINE.fa.md` است؛ اینجا شکل کلی:

1. **تفکیک بدنه** — پیام به بلوک‌های سرعنوان و ردیف شکسته می‌شود.
2. **مالک ردیف** — هر ردیف باید یک مالک داشته باشد: یا `pending` (سرعنوانِ در
   انتظار) یا `heading` (سرعنوانِ گروه).
3. **استخراج مبلغ** — مبلغی که **برچسب واحد پول** دارد نامزد می‌شود.
4. **گارد ابهام** — اگر دقیقاً یک نامزد باشد، پذیرفته می‌شود؛ وگرنه رد می‌شود.
5. **استخراج مشخصات** — سایز، ضخامت، ابعاد، گرید از عنوان و جزئیات.

### سه قاعده‌ای که با اندازه‌گیری پیدا شدند

این‌ها حدس نبودند؛ با اجرای موتور روی پیام واقعی پیدا شدند.

**۱. مالک ردیف بعد از اولین مبلغ پاک نمی‌شود.**
پیش‌تر بعد از اولین ردیف قیمت‌دار، `pending` خالی می‌شد و بقیهٔ ردیف‌های همان
فهرست بی‌مالک می‌ماندند و دور ریخته می‌شدند. اندازه‌گیری: یک فهرست ۸ ردیفی
تیرآهن → **۱** ردیف استخراج می‌شد. حالا `owner = pending ?? heading` و ۸ → ۸.

**۲. گارد ابهام نامزدها را می‌شمارد، نه همهٔ اعداد را.**
پیش‌تر شرط `numbers.length != 1` بود. پس یک عدد بی‌ربط در متن — سال شمسی
(`۱۴۰۵`) یا کد سفارش (`۱۰۲۴`) — باعث می‌شد مبلغِ دارای برچسب واحد پول هم سفید
شود. حالا شرط `candidates.length != 1` است. ابهام واقعی (`۱۲۰۰۰۰ یا ۱۲۵۰۰۰`) و
بازهٔ صریح همچنان رد می‌شوند.

**۳. مبلغ همان‌طور که منبع نوشته، نگه داشته می‌شود.**
`amountRaw` (`مبلغ استخراج‌شده`) در ایندکس حمل می‌شود. بدون آن، کارتی که از
ایندکس بازسازی می‌شد برای منبعی که `۴۱,۰۰۰ تا ۴۳,۰۰۰` نوشته بود **«بدون قیمت»**
چاپ می‌کرد.

## ۶) ایندکس مشتق

`RowFacts` یک payload را به یک ردیف ایندکس تبدیل می‌کند.

### ۶.۱ کلید: اثر انگشت payload

```dart
String payloadFingerprint(String payload)  // طول + FNV-1a
```

کلید اصلی `range_index` همین اثر انگشت است، نه `id` ردیف. نتیجه:

- payload دست‌نخورده **هرگز دوباره parse نمی‌شود**، حتی بعد از ری‌استارت.
- payload بازنویسی‌شده کلید تازه می‌گیرد و یک‌بار بازسازی می‌شود.

اندازه‌گیری: خودِ این تابع ۱.۷ میکروثانیه به‌ازای هر ردیف است — ارزان. یک
اندازه‌گیری اولیه آن را متهم کرده بود که رد شد.

### ۶.۲ نسخهٔ اشتقاق

`RowFacts.derive` (اکنون `'v5'`) در ستون `derive` ذخیره می‌شود و
`RowFacts.isCurrent` آن را با `source_date_raw` و `amount_raw` بررسی می‌کند.
افزودن یک ستون مشتق = بالا بردن این نسخه؛ بقیه خودکار اتفاق می‌افتد.

### ۶.۳ چه چیزی در ایندکس است

ستون‌های ایندکس طوری انتخاب شده‌اند که فیلتر **یک مقایسهٔ رشته یا عدد** باشد:

- `size_label` / `thickness_label` / `dimensions_label` / `grade_label` — برچسب
  رشته‌ای، برای نمایش و مقایسهٔ متنی.
- `size_num` / `thickness_num` — همان‌ها به شکل عددی، یک‌بار parse شده.
- `haystack` — متن نرمال‌شده برای مرز شهر.
- `search` — متن جست‌وجو.
- `facts` / `prices` — بستهٔ فشردهٔ مشخصات و جدول تبدیل قیمت.
- `amount_raw`، `source_date_raw`، `amount`، `currency`، `market_at`.

### ۶.۴ ساختن ایندکس

`_indexPayloads` سه مرحله دارد:

1. **یافتن کلیدهای به‌روز** — یک پرس‌وجوی `IN (…)` به‌ازای هر ۴۰۰ کلید.
2. **اشتقاق روی ایزولیت کارگر** — `compute(_deriveIndexRows, chunk)`.
3. **درج دسته‌ای کرانه‌دار** — برای هر تکهٔ حداکثر ۴۰۰ردیفی، یک batch با
   `noResult: true`. تمام batchها داخل تراکنش بیرونی‌اند؛ خطای تکهٔ بعدی نیز
   کل snapshot را rollback می‌کند. صف تمام ردیف‌های ایندکس یک‌جا نگهداری نمی‌شود.

پیش‌تر هر سه مرحله **به‌ازای هر ردیف** یک پرس‌وجو/درج جدا و یک parse روی ایزولیت
رابط کاربری بود. اعداد در بند ۱۰.

---

### ۶.۵ خواندن صفحه‌ای در ۰.۸.۵

`latest/latestFor`: داخل یک تراکنش snapshot، پیمایش `rowid > after` و decode
حداکثر ۴۰۰ ردیف در هر isolate. تعداد مدل‌های نهایی محدود نشده است.

`rangeIndexRows`: جدول TEMP فقط `(position, kind, source_row)` نگه می‌دارد؛
selection همان history در پنجره، latest و نمایندهٔ historyهای orphan است.
صفحه‌ها با position و join روی کلید مبدأ خوانده می‌شوند؛ lookup/بازسازی فقط برای
همان صفحه است. payloadهای کامل آرشیو هم‌زمان در Dart نگهداری نمی‌شوند.
جدول موقت در finally حذف می‌شود. `NOT INDEXED` در بخش کلیدهای latest ترتیب
پیمایش جدول را مطابق مسیر قبلی نگه می‌دارد. duplicateها و ترتیب با مسیر قدیمی
در آزمون سرد/گرم مقایسه شده‌اند.

حد ۴۰۰، سقف کار موقت است؛ نه سقف اندازهٔ آرشیو یا کل RAM. لیست مدل‌های فعلی و
ایندکس نهایی هنوز با داده رشد می‌کنند.

## ۷) تصویر رنج و نامزدها

### ۷.۱ `RangeSession`

یک نقطهٔ تماس برای تب رنج: ایندکس در حافظه، کارگر مقیم، و کش پاسخ‌ها.

```
dataToken = 's{session}.d{epoch}.w{windowDays}'   // هویت خودِ داده
token     = 'i{epoch}-{minuteBucket}'              // هویت پاسخ‌ها
```

`invalidate()` نسل داده و epoch را جلو می‌برد و وضعیت مشتق را دور می‌ریزد؛
نصب موفق snapshot تازه نیز epoch را تغییر می‌دهد. خواندن جاری باید پیش از
تغییر window تمام شود و نتیجهٔ نسل منقضی‌شده حق نصب دوباره در session ندارد.
هم‌زمانی یک window یک خواندن را شریک می‌شود؛ window متفاوت بعد از آن جدا خوانده می‌شود. یک دقیقهٔ
جدید فقط `bucket` را جلو می‌برد — ایندکس دوباره خوانده **نمی‌شود**، ولی پاسخ‌های
کش‌شده دور ریخته می‌شوند (چون مرز تازگی و پنجرهٔ انتخابی با زمان جابه‌جا می‌شود).

### ۷.۲ کارگر مقیم

`RangeWorker.shared` ردیف‌ها را نگه می‌دارد تا تأیید بعدی هیچ آماده‌سازی نداشته
باشد. اگر `dataToken` نخورد، کارگر `dispose` و از نو بارگذاری می‌شود — وگرنه
ممکن است با ردیف‌های آرشیو دیگری پاسخ دهد.

در ۰.۸.۵ این کارگر **خودکار در startup/reload/پایان refresh گرم نمی‌شود**؛
تأیید کاربر در تب رنج آن را آماده می‌کند. شروع refresh و dispose کنترلر کارگر
قدیمی را آزاد می‌کنند. کارگر بیکار با پیام بیدار می‌شود، نه با حلقهٔ تایمر صفرمدت؛
پورت خطا نیز در reset بسته می‌شود.

### ۷.۳ صفحه‌بندی نامزدها

`CandidateSet` فقط `candidatePrebuild = 60` ردیف را از پیش می‌سازد؛ بقیه به شکل
`Map` خام می‌مانند و هنگام اسکرول ساخته می‌شوند (`extend`). ده هزار ردیف در
دامنه، هزینهٔ ده هزار آبجکت در فریم اول ندارد.

**استثنا:** مرتب‌سازی بر اساس قیمت. ارزان‌ترین پیشنهاد ممکن است آخرین ردیف
دامنه باشد، پس در این حالت همهٔ ردیف‌ها یک‌بار ساخته و سپس مرتب می‌شوند.

### دریافت

`SourceClient.fetch(endpoint, windowDays, pageLimit)` صفحه‌های عمومی کانال را
به سقف صفحهٔ صریح محدود می‌کند. برای پنجرهٔ زمانی محدود، وقتی صفحه‌ای فقط
قدیمی‌تر از بازه باشد توقف می‌کند و ردیف بیرون بازه را ذخیره نمی‌کند؛ در حالت
«همهٔ زمان‌ها» cutoff ضمنی ۷روزه ندارد و فقط سقف صفحه اعمال می‌شود. اسکن
WorkManager هر نوبت ۱۶ منبع چرخشی و حداکثر ۲ صفحه از هر کانال می‌خواند.

پارس HTML روی ایزولیت پس‌زمینه انجام می‌شود (`compute`).

### ادب شبکه

- همزمانی ۲ کارگر.
- ۴۵۰ میلی‌ثانیه فاصله بین منبع‌ها.
- بدون retry تهاجمی.
- خطای یک منبع، دادهٔ قبلی‌اش را پاک نمی‌کند؛ فقط در `sync` گزارش می‌شود.

## ۹) چرخهٔ نوسازی

```
refresh()
  ├─ busy = true؛ نامعتبرکردن session/cache و آزادکردن کارگر قبلی
  ├─ اگر baseline خوانده نشده: خواندن صفحه‌ای latest
  ├─ دو کارگر دریافت:
  │    fetch(e) → saveSnapshot(e) → صف _publishEndpoint(e)
  │                                 [فقط ردیف‌های همان منبع، بدون رد انتشار هم‌زمان]
  │    ۴۵۰ ms فاصله
  └─ finally:
       busy = false؛ نامعتبرکردن ایندکس تغییرکرده؛ پایان صف انتشار
       فقط syncStates در حالت عادی
       reload کامل فقط اگر انتشار شکست خورده/ baseline آماده نبوده باشد
       prepareCandidates() برای پنجرهٔ قیمت؛ بدون warm خودکار RangeWorker
```

### چرا publish افزایشی است

نسخهٔ پیشین به‌جای `_publishEndpoint` کل آرشیو را با `reload()` دوباره decode
می‌کرد و آن را با یک پنجرهٔ ۲.۵ ثانیه‌ای محدود می‌کرد. این کار «هر منبع یک
آرشیو کامل» را به «هر ۲.۵ ثانیه یک آرشیو کامل» کاهش می‌داد، ولی حذف نمی‌کرد: در
یک نوسازی ۱۸ ثانیه‌ای حدود هفت بار، هر بار یک کپی کامل از همهٔ ردیف‌های ذخیره‌شده.

حالا هر منبع فقط ردیف‌های **خودش** را decode می‌کند و جایگزین می‌کند:

```dart
quotes = [for (final q in quotes) if (q.endpoint != endpoint) q, ...rows];
```

### چرا ایندکس وسط نوسازی ساخته نمی‌شود

دو دلیل:

1. **درستی** — وسط نوسازی آرشیو نیمه‌نوشته است؛ ایندکسی که حالا ساخته شود همان
   آرشیو نیمه‌نوشته را توصیف می‌کند.
2. **حافظه** — نگه‌داشتن ایندکس یعنی دو نمایش کامل از آرشیو همزمان در حافظه:
   ردیف‌های decode‌شده *و* ردیف‌های پهن ایندکس.

پس در طول نوسازی `prepareCandidates` زود برمی‌گردد و تب قیمت با فیلتر کلاسیک روی
ردیف‌های موجود پاسخ می‌دهد. ایندکس یک‌بار، در پایان، ساخته می‌شود.

### نتیجهٔ جاری ۰.۸.۵

۰.۸.۵. علت قطعی مرگ فرایند Android بدون شواهد سیستم تعیین نشده است.

### ۱۰.۳ گلوگاه واقعی

`RowFacts.ofQuote` به‌ازای هر ردیف **۱۱۶۹ میکروثانیه** هزینه داشت، در حالی که
ساختن خودِ `Quote` تنها ~۸۰ میکروثانیه بود. تجزیهٔ آن:

| جزء | میکروثانیه/ردیف |
| --- | --- |
| `announcementKey` | ۴۸۱ |
| `exactProductKey` | ۴۲۳ |
| `ProductFacts.of` | ۴۲۲ |
| بقیه | ~۲۳۰ |

علت: زنجیرهٔ فراخوانی

```
ofQuote → ProductFacts.of           (۱)
        → exactProductKey → ProductFacts.of   (۲)
        → announcementKey → rangeGroupKey → exactProductKey → ProductFacts.of   (۳)
```

یعنی `ProductFacts.of` **سه بار برای هر ردیف**. به‌علاوه چهار `late final`
برچسب، `_field` را دو بار با همان شرط صدا می‌زدند (۸ فراخوانی به‌جای ۴)، و
`latin` به‌ازای هر کلید و مقدار جزئیات یک‌بار اجرا می‌شد در حالی که واژگانش در
کل آرشیو تکراری است.

### ۱۰.۴ اصلاح‌ها

1. `ProductFacts.of` یک‌بار در `ofQuote` و پاس دادن آن به `exactProductKey`،
   `rangeGroupKey` و `announcementKey` (پارامتر اختیاری؛ همهٔ فراخوانی‌گاه‌های
   موجود سازگار ماندند).
2. هر برچسب `_field` را یک‌بار صدا می‌زند.
3. `latin` memo شد، با **کش کرانه‌دار** (۴۰۹۶ ورودی، تخلیهٔ کامل). کرانه‌دار بودن
   عمدی است: یک آرشیو بزرگ نباید بتواند کش را بی‌حد رشد دهد.
4. `RegExp`های داغ به سطح فایل منتقل شدند (پیش‌تر در حلقه کامپایل می‌شدند).
5. `_indexPayloads`: پرس‌وجوی `IN (…)` دسته‌ای، اشتقاق روی ایزولیت کارگر، درج
   دسته‌ای.
6. publish افزایشی به‌جای decode کامل آرشیو (بند ۹).
7. `rangeIndexRows` رشته‌های payload را برای ردیف‌های ایندکس‌شده زودتر رها
   می‌کند؛ فقط ترتیب کلیدها تا پایان نگه داشته می‌شود.

### ۱۰.۵ نتایج اندازه‌گیری‌شده

همه روی یک ماشین، آرشیو ۱۲٬۰۰۰ ردیفی، مقایسهٔ کامیت پایه با همین تغییرات:

| مسیر | پیش | پس | نسبت |
| --- | --- | --- | --- |
| اشتقاق یک ردیف | ۱٬۴۶۳ µs | **۱۹۶ µs** | ۷.۵× |
| نوشتن ۶۰ منبع × ۲۰۰ ردیف | ۲۹٬۳۲۴ ms | **۵٬۰۷۴ ms** | ۵.۸× |
| `saveSnapshot` ۴۰۰ ردیف نو | ۱٬۱۷۰ ms | **۱۶۹ ms** | ۶.۹× |
| `rangeIndexRows` سرد | ۲۵٬۵۲۵ ms | **۳٬۵۹۰ ms** | ۷.۱× |
| `rangeIndexRows` گرم | ۴۰۴ ms | **۴۵۰ ms** | ≈ |
| `selectCandidates` | ۴۸ ms | **۳۰ ms** | ۱.۶× |
| `refresh()` کامل ۸۲ منبع | ۲۸٬۹۰۶ ms | **۲۱٬۸۰۰ ms** | ۱.۳× |
| RSS پس از نوشتن ۱۲هزار ردیف | ۳۱۰ MB | **۲۵۴ MB** | ‎−۵۶ MB |

دو عدد تفکیکی که دلیل اصلاح ۵ را نشان می‌دهند:

| عملیات | تک‌تک | دسته‌ای |
| --- | --- | --- |
| `SELECT` برای ۱۲هزار کلید | ۳٬۱۷۴ ms | **۳۱ ms** (۱۰۲×) |
| `INSERT` برای ۱۲هزار ردیف | ۲٬۵۷۹ ms | **۱۲۲ ms** (۲۱×) |

### ۱۰.۶ آنچه صادقانه حل‌نشده ماند

- **`peak RSS` در نوسازی واقعی تقریباً تغییر نکرد** (۲۹۹ → ۲۹۷ MB). کاهش حافظه
  در *نوشتن* آشکار است (۳۱۰ → ۲۵۴) ولی اوجِ نوسازی را پایین نیاورد. تجزیهٔ
  حافظه نشان داد هیچ نگهدارندهٔ واحدی فاجعه نیست: ۴٬۹۲۰ آبجکت `Quote` ≈ ۳۱ MB
  و ۶٬۷۲۴ ردیف ایندکس ≈ ۱۹ MB. کاهش بیشتر نیازمند تغییر ساختاری است (نگه
  نداشتن کل آرشیو به شکل `Quote`)، نه بهینه‌سازی.
- **`rangeIndexRows` گرم ۴۰۴ → ۴۵۰ ms** یعنی اندکی کندتر شد؛ هزینهٔ ساخت
  `orderedHashes`. در برابر ۲۵ ثانیه‌ای که از مسیر سرد کم شد، معاملهٔ درستی است،
  ولی پنهانش نکردیم.
- این اندازه‌گیری‌ها روی `sqflite_common_ffi` و یک ماشین لینوکسی است. روی دستگاه،
  هر رفت‌وبرگشت دیتابیس یک پرش platform-channel است، پس سودِ دسته‌کردن
  پرس‌وجوها روی گوشی ممکن است متفاوت باشد؛ بزرگ‌تر بودن سود بدون اندازه‌گیری دستگاه اثبات نشده است.
