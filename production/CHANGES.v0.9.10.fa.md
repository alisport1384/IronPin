# تغییرات نسخهٔ ۰.۹.۱۰ (build 32) — سرعت خواندن و جستجو در آرشیوهای بزرگ

گزارش کاربر: با حدود ۳۰٬۰۰۰ ردیف، خواندن و جستجو به‌شدت کند و اپ دچار فریزهای
ثانیه‌ای می‌شود. این نسخه فقط همان گلوگاه را هدف می‌گیرد؛ هیچ قاعدهٔ قیمتی،
جستجوی معنایی، رنج‌گیری یا قالبی تغییر نکرده است.

---

## ۱) عیب‌یابی اندازه‌گیری‌شده (پیش از تغییر)

بنچمارک پایه روی همین درخت (ابزار خود پروژه، `tool/perf_archive.dart` و
`test/scale_100k_test.dart`، محیط ساخت x86):

| مسیر | ۱۰۰٬۰۰۰ ردیف (۵۰٬۰۰۰ جاری + ۵۰٬۰۰۰ تاریخچه) |
| --- | ---: |
| راه‌اندازی + آماده‌سازی نامزدها (`initMs`) | ۳۵۸۲ ms |
| مرتب‌سازی صعودی کل دامنه (`sortAscMs`) | ۶۲۴ ms |
| دو جستجوی معنایی (`searchMs`) | ۱۲۰۲ ms |
| تأیید رنج (`rangeConfirmMs`) | ۱۰۸۰ ms |

ریشهٔ فریز، «زمان کل» نبود؛ این بود که انتخاب نامزدهای تب قیمت
(`selectCandidates` روی کل ایندکس + مرتب‌سازی wires) **به‌صورت همگام روی
ایزولیت UI** اجرا می‌شد: هر کلیدِ جستجو یک بلاک چندصدمیلی‌ثانیه‌ای تا
ثانیه‌ای روی همان ایزولیتی که فریم می‌کشد. روی گوشی ۳۲بیتی قدیمی (مخاطب
فایل armeabi-v7a) این بلاک چند برابر می‌شود.

مسیرهای دیگرِ خواندن از قبل سالم بودند و دست نخوردند: SQLite تنها مرجع
پول است، `range_index` اشتقاقِ زمانِ نوشتن است، `store.latest()` روی
ایزولیت کارگر decode می‌شود و رندر لیست `ListView.builder` تنبل است.

## ۲) اصلاح‌ها

- **انتخاب تکه‌تکهٔ نامزدها** (`lib/domain/range_projection.dart`،
  `lib/data/range_session.dart`): منطق `selectCandidates` عیناً به کلاس
  وضعیت‌دار `CandidateSelector` منتقل شد (تابع همگام قدیم همان حلقه است،
  پس دو مسیر هرگز اختلاف ندارند). در آرشیوهای بالای ۴٬۰۰۰ ردیف ایندکس،
  `RangeSession.candidates` اسکن را در برش‌های ۱٬۲۰۰ ردیفی اجرا و بین
  هر برش ایزولیت UI را آزاد می‌کند؛ طولانی‌ترین بلاک همگام از کل اسکن
  به یک برش (~چند میلی‌ثانیه) می‌رسد. اگر آرشیو وسط اسکن باطل شود، پاسخ
  کهنه منتشر نمی‌شود (`StateError`).
- **مرتب‌سازی یک‌بار، نه هر کلید**: ایندکس هنگام بارگذاری یک‌بار
  `market_at DESC, id ASC` مرتب می‌شود و انتخاب، همان ترتیب را حفظ
  می‌کند؛ مرتب‌سازی wires از مسیر هر جستجو حذف شد.
- **نمایش نتیجهٔ قبلی حین آماده‌سازی** (`lib/data/controller.dart`):
  تا وقتی مجموعهٔ تازه آماده نشده، تب قیمت همان مجموعهٔ قبلی را نشان
  می‌دهد؛ مسیر جایگزینِ سابق (`filtered`) با هر کلید یک فیلتر کامل روی
  همهٔ `Quote`های decodeشده (روی ۵۰٬۰۰۰ آبجکت) استارت می‌زد.
- **دیبانس جستجو**: در آرشیوهای بالای ۲٬۰۰۰ ردیف از ۷۰ به ۳۰۰ میلی‌ثانیه.
- **ایندکس‌های SQLite تازه** (`range_index(market_at)` و
  `range_index(endpoint, id, fetched_at)`): بدون bump اسکیما؛ روی هر باز
  شدن دیتابیس با `IF NOT EXISTS` برای آرشیوهای قبلی هم ساخته می‌شوند.

## ۳) چه چیزی عمداً انتخاب نشد

SQLite FTS5 روی SQLite سیستمی اندروید (به‌ویژه API 21، کف این اپ)
تضمین‌شده نیست و FTS4/unicode61 نیز معنای جستجوی فعلی (تشخیص خانواده،
سایز/ضخامت دقیق و رد اقلام غیرفلزی با `ProductQuery`) را حفظ نمی‌کند؛
پس به‌جای مهاجرت پرریسک، همان انتخاب دقیق فعلی زمان‌بندیِ درست گرفت.

## ۴) سنجش پس از تغییر

- `flutter analyze` — بدون مسئله.
- `flutter test` — ۵۰۹ تست سبز (۵۰۷ قبلی + ۲ تست تازهٔ
  `test/candidate_async_test.dart` که برابری خروجی مسیر تکه‌تکه با مسیر
  همگام، حفظ ترتیب جدیدترین‌اول، وجود ایندکس‌ها و بازپس‌دادن ایزولیت UI
  وسط اسکن را ثابت می‌کنند).
- بنچمارک ۱۰۰٬۰۰۰ ردیف پس از تغییر: `initMs=3418`، `searchMs=1067`
  (زمان کل ذاتاً همان اسکن است؛ تفاوت این است که دیگر هیچ بلاک
  ثانیه‌ای روی ایزولیت UI نیست و تایپ/اسکرول وسط جستجو زنده می‌ماند).

## ۵) امضا و تحویل این نسخه

- فایل تست این تحویل با کلید پایدار محلی این محیط
  (`CN=IronPin Local Sideload`) امضا شده است؛ این کلید با کلید ریلیزهای
  ۰.۹.۶ تا ۰.۹.۹ (`CN=IronPin Sideload`، SHA-256 گواهی
  `16fe4f74…4c4ee`، فقط در GitHub Secrets) **یکی نیست**، پس روی نصب
  ۰.۹.۹ رسمی نصب نمی‌شود: برای تست، اول از داخل برنامه «پشتیبان کامل»
  بگیرید، نسخهٔ قبلی را حذف و این فایل را نصب کنید، بعد پشتیبان را
  بازیابی کنید.
- نسخهٔ نهاییِ قابل‌نصب روی ۰.۹.۹ باید با همان کلید پروژه ساخته شود:
  یا با push به GitHub (ساخت Actions با Secrets) یا با در اختیار گذاشتن
  فایل keystore پروژه.
